# UI internationalization (static app chrome)

How the **app chrome** (nav, buttons, labels, headings, placeholders, dates, role
labels, server-action error/validation messages) is translated. This is **separate**
from the LLM content-translation layer (`lib/translation/`, `lib/ai/`), which handles
user-authored data — see [`docs/features.md`](features.md) §9. Both honor the same
per-user `profiles.preferred_language`.

No i18n library — a hand-rolled typed dictionary, to keep the client bundle small
(mobile / low-end Android). English + Spanish today; structured so a 3rd language is
a one-file add.

## Files (`src/lib/i18n/`)

| File | Role |
|---|---|
| `en.ts` | **Source of truth.** Nested string dictionary by area (`common`, `nav`, `items`, `errors`, …). `export type Dict = typeof en`. Intentionally **not** `as const`, so leaves widen to `string` and `es` can supply Spanish while key structure is still enforced. |
| `es.ts` | `export const es: Dict = {…}` — the `: Dict` annotation makes `tsc` fail on any missing/extra/renamed key. Spanish quality isn't type-enforced (human-validated separately); **structure is**. |
| `index.ts` | Server-facing: `getDictionary(lang)`, `asLang(value)`, `resolveKey(dict, 'a.b.c')` (for Zod keys), re-exports `interpolate`, `Dict`, `Lang`. |
| `interpolate.ts` | `interpolate(template, params)` replacing `{token}`. No dict imports → safe in client + server. |
| `client.tsx` | `'use client'`: `LanguageProvider` + `useT()`. Dict/Lang imported **type-only** (erased), so neither dictionary enters the client JS bundle. |
| `server.ts` | `'server-only'`: `getCookieLang()`, `setCookieLang(lang)`, `getActionDict(preferred?)`. |

## Delivery

- **Server components / pages / `format.ts`**: `const dict = getDictionary(lang)` →
  `dict.items.heading`. `lang` is `profile.preferredLanguage` (logged-in) or the cookie.
- **Client components**: `const { dict, t } = useT()` → `dict.items.addItem`,
  `t(dict.dashboard.progress, { done, total })`. The provider (wrapping `(app)` and
  `(auth)` layouts) receives the **already-resolved active dict** as a prop — the only
  language that travels to the browser, in the RSC payload, not the JS bundle.
- **`<html lang>`** (root layout) and the logged-out **auth pages** read the `lang`
  cookie (default `en`). The cookie is written on **signup** (picked language),
  **login** (from `profile.preferred_language`), and **Settings** language change, so
  it converges to the user's real preference.

## Server-action error/validation messages

The `{ error: string }` contract to client render sites is unchanged. Inside actions:
- **Zod**: put a stable dictionary KEY in the message slot
  (`z.string().min(1, 'errors.items.nameRequired')`), then `resolveKey(dict, parsed.error.issues[0].message)`
  on return.
- **Guards** (`requireBuilder` etc.) resolve the dict from the caller's profile language
  (or `getActionDict()` → cookie when there's no profile) and return localized strings;
  on success they also return `dict` so the action localizes its own messages.

## How to add a string

1. Add the key to **both** `en.ts` and `es.ts` (same path). `tsc` fails if you miss one.
2. Use it: `dict.area.key` (server) or via `useT()` (client). Parameterized? Use
   `{token}` + `interpolate`/`t`.
3. For an action error, add it under `errors.<area>.*` and reference it (or use the
   dotted key in a Zod message + `resolveKey`).

## How to add a language (v2)

1. Add the code to the `Lang` union (`index.ts`) and the `LANGUAGES` const in
   `schema.ts` (drives the DB CHECK).
2. Create `xx.ts` mirroring `en.ts` (typed `: Dict`); register it in `DICTS` in `index.ts`.
3. Add the locale in `format.ts` (`LOCALE` map) and the language's own name in
   `dict.languages`. Surface it in the Settings + signup language pickers.

## Out of scope
Timezone **zone** labels stay English (proper-noun city names); only the picker's
surrounding UI + region group headers translate. Numbers/currency (none in the app yet).
